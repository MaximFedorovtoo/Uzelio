# Хранилище встроенного мессенджера Uzelio

Этот модуль подключён к Android и Windows приложениям. Android `UzelioApplication`
владеет одним `CompletableFuture<MessengerRuntime>`, Windows запускает `DesktopMessenger`
из `DesktopMain`. Ошибка открытия остаётся ошибкой future: plaintext fallback,
автоматического удаления базы или замены личности нет.

## Что реализовано

- `MessengerRuntime`: блокировка профиля до проверки наличия файлов, создание или
  открытие единственного экземпляра, владение хранилищем и освобождение ресурсов.
- `DeviceKeyVault`: случайный 256-битный ключ базы, атомарно записанный в обёртке ОС.
  Windows — DPAPI CurrentUser, Android — неэкспортируемый AES-256/GCM AndroidKeyStore.
  Android данные находятся в `getNoBackupFilesDir()`, резервное копирование приложения отключено.
- `JdbcMessageStore` / `AndroidMessageStore`: зашифрованные DB и WAL, FULL/MEMORY,
  транзакционные records и запрет использования callback после завершения.
- `TransactionSignalStore`: все состояния libsignal, доверенные identity, одноразовые
  EC/PQ prekeys и signed prekeys сохраняются в той же транзакции, что сообщения.
  Объекты ratchet заново десериализуются при каждой операции, mutable cache отсутствует.
- `SignalMessenger.send`: точный ciphertext в outbox и обновлённый сеанс сохраняются
  вместе. Повтор operationId возвращает прежний ciphertext; другое содержимое с тем
  же id отклоняется. `receive` сохраняет plaintext, сеанс и локальную квитанцию вместе;
  повтор точного wire-пакета не создаёт новое сообщение и не повторяет расшифрование.

`trustPeer` — явное закрепление уже проверенного ключа устройства. Он не выполняет
проверку сертификата/членства и не допускает автоматическую замену существующего ключа.
Слой авторизации должен проверить устройство до вызова этого метода. Группы запрещены.
Адрес локального устройства создаётся при первом запуске и хранится в encrypted DB.

## Граница атомарности и отката

Отдельная защищённая `commit.anchor` содержит случайный token последнего commit.
Перед DB transaction сохраняется PENDING(old,next), внутри DB изменяются состояние
libsignal, сообщения, outbox/receipt и token; после commit сохраняется CLEAN(next).
Результат отправки/приёма возвращается только после финализации anchor.

После подтверждённого rollback живой процесс может восстановить CLEAN(old).
После перезапуска PENDING+next завершается; PENDING+old блокирует профиль: авария
до commit и откат уже записанной базы неразличимы. Неоднозначный commit также
блокирует экземпляр. UI восстановления пока не реализован; файлы не удаляются.

Защита обнаруживает замену базы старым целым согласованным снимком при сохранённой
актуальной anchor. Это НЕ аппаратный монотонный счётчик и НЕ хеш всех записей:
выборочное воспроизведение старых аутентифицированных страниц с сохранением новой
страницы token, либо откат базы вместе с anchor, этим механизмом не обнаруживается.
Защита от скомпрометированного процесса/аккаунта ОС также не обещается.

`force(true)` и атомарное переименование проверены при завершении процесса.
Поведение при реальной потере питания/откате накопителя не доказано; это отдельный
аппаратный критерий. Java/JNI могут хранить внутренние копии секретов, очистка массивов
выполняется best effort. Android Keystore не обязательно аппаратный на каждом устройстве.

## Личные чаты внутри Uzelio

Навигация Android и Windows: «Главная / Чаты / Профиль»; карта и трафик открываются
с главной. Нативный экран использует настоящие контакты и зашифрованную историю,
сохраняет черновик при обновлении сообщений и не подставляет демонстрационные чаты.

При первом открытии чатов приложение запускает отдельный TLS listener на TCP 39283.
Он не зависит от режима раздачи/VPN. На Android исходящие сокеты привязываются
к актуальной физической сети. Контакты обмениваются отдельными приглашениями
через доверенный канал: код подписан Signal identity и содержит адрес устройства,
TLS fingerprint и свежие одноразовые prekeys. Обе стороны добавляют друг друга.
Приглашение действует семь дней; для каждого нового контакта нужен новый код.
Поле адреса в диалоге приглашения предзаполняется частным IPv4-адресом устройства
(функция `LocalAddress`), но за NAT этот адрес сам по себе недоступен.

TLS проверяет закреплённый сертификат сервера и известный сертификат клиента.
Внутри передаются только Signal ciphertext. Исходящий текст, состояние ratchet
и очередь записываются одной транзакцией. Входящая история и ratchet тоже атомарны.
Состояние «Доставлено» означает получение зашифрованного Signal ACK от адресата
после сохранения сообщения; оно не означает прочтение. Потеря ACK оставляет точный
исходный ciphertext в очереди; повтор не добавляет дубль, ACK также повторяется
без повторного шифрования. Неподтверждённая очередь ограничена 128 сообщениями,
контакты — 256, текст — 32 КиБ UTF-8. Экран показывает последние 500 сообщений.
Одновременно работают до четырёх исходящих и четырёх входящих соединений;
один недоступный контакт занимает не больше одного исходящего работника.
Каждый открытый сокет имеет независимый абсолютный срок 30 секунд, включая TLS,
чтение и запись: медленная передача отдельных байтов не продлевает этот срок.

Текущий сетевой путь — прямое соединение с адресом из приглашения. Устройства
должны быть взаимно доступны: локальная сеть либо маршрутизируемый адрес/порт.
Автоматический обход NAT не реализован; если прямой путь невозможен, используется
relay без хранения (см. ниже). Адрес существующего контакта пока неизменяем:
смена endpoint требует отдельного протокола обновления, а не сброса доверенных ключей.
Android может остановить процесс в фоне: постоянная фоновая доставка и push пока
не реализованы. После запуска нужно открыть «Чаты», чтобы запустить приём/повторы.

## Relay без хранения

Прямой путь требует взаимной доступности. Для разных сетей приглашение может нести
адрес relay-узла в виде `host:port:pin`, где pin — отпечаток самоподписанного
сертификата узла. Обе стороны подключаются к relay исходящими TLS-соединениями,
поэтому NAT на стороне участников не мешает: доступным должен быть только узел.

Relay запускается командой `Uzelio.exe --relay [порт]` (по умолчанию 39284) и
печатает готовую строку `relay=host:port:pin`. Узел держит таблицу подключённых
устройств и пересылает кадры Signal: не пишет их на диск, не хранит очередь и не
ведёт журнал содержимого. Если получатель не подключён, отправитель получает отказ
и сохраняет сообщение в своей очереди, пока получатель не вернётся. Лимиты: кадр
до 256 КиБ, до 512 устройств, 8 обработчиков, 30 секунд простоя соединения.
Relay видит имена устройств, размеры и время кадров, но не текст: внутри остаётся
Signal-шифртекст, а квитанция доставки формируется конечным устройством.

Адрес вставляется в диалог «Моё приглашение» (поле Relay); пустое поле означает
только прямое соединение. Прямой путь пробуется первым, relay используется при
его отказе. Проверено 26.10.2026: два участника с заблокированным прямым путём
обмениваются текстом и квитанцией через relay; при отключённом получателе
сообщение остаётся `queued` и доставляется после возврата — тесты `ChatRelayTest`.

## P2P-канал для сопряжённых устройств

Если устройства уже установили прямой канал для раздачи (WebRTC/ICE, подписанный
SDP), чат едет по нему, не требуя ни статического адреса, ни проброса портов:

- на Android и Windows поток с меткой `uzel.chat.v1.<uuid>` бриджится на локальный
  TLS-listener чата (39283), а `uzel.stream.v1.<uuid>` — на порт VPN-узла;
- внутри потока тот же pinned mTLS и Signal-кадры, поэтому P2P даёт только транспорт
  и не ослабляет доверие;
- сессия ищется по отпечатку TLS-сертификата контакта — он совпадает с отпечатком
  устройства в паре, потому что чат, узел и сопряжение используют одну identity;
- порядок доставки: прямой адрес → P2P-поток → relay.

Ограничения: P2P работает только для уже сопряжённых устройств и только пока жив
парный транспорт (раздача включена). Если TLS-listener чата ещё не поднят, входящий
P2P-поток отклоняется, а сообщение остаётся в очереди отправителя. Симметричный
NAT/CGNAT ICE не пробивает — там остаётся relay.

Проверено 26.10.2026: `ChatP2PTransportTest` — при недоступном прямом адресе
сообщение проходит через P2P-поток и получает квитанцию, без живой сессии остаётся
`queued`; `TraversalChatStreamTest` — на реальных native ICE-пирах поток
`uzel.chat.v1` приходит в порт чата, обратный путь работает.

## Уведомления

Новое сообщение, пришедшее пока приложение запущено, показывается системным
уведомлением: на Android — канал «Чаты» (нажатие открывает раздел), на Windows —
всплывающее сообщение в области уведомлений. Если раздел «Чаты» уже открыт,
уведомление не дублируется. Повторная доставка того же шифртекста (ретрай,
перезапуск) уведомление не повторяет — оно привязано к новой записи в истории.

Проверено: `ChatNotificationTest` — одно уведомление на сообщение, ноль на квитанцию
и на повторную доставку.




Следующие этапы: RAM-only relay и NAT traversal, аутентифицированное обновление
маршрутов, несколько устройств, синхронизация и восстановление исключительно
с устройств участников, группы и пагинация истории. Без доступной копии участника
восстановить утраченную историю невозможно.

## Локальные проверки

Сборка: portable Java21.0.12.1+1, Gradle8.13, AGP8.10.1, compileSdk36, minSdk29.
Исходный Java-код сохраняет уровень17; Windows runtime требует21 из-за libsignal.
Зависимости бесплатные, условия AGPLv3 libsignal и notices см. `THIRD_PARTY_NOTICES.txt`.

```
gradle :core:test :messenger:test :desktop:test :app:testDebugUnitTest :app:assembleDebug
```

Android instrumentation: пакет `org.uzel.app.messenger`, только локальный эмулятор.
Проверены API29/x86_64, реальный Keystore/SQLCipher/libsignal и повторный запуск процесса
с той же identity. ARM64, остальные API и 16-КиБ устройства требуют отдельных прогонов.
Windows tests выполняют DPAPI/JDBC, реальные libsignal callbacks и дочерние процессы,
аварийно завершаемые до/после commit. Диагностические данные тестов не публикуются.

Локальное сравнение `ChatStorageCostTest` (20 попеременных записей на вариант,
одинаковые зашифрованные профили и payload): исходная запись Signal — медиана
19,428 мс, 49,8 операций/с, CPU текущего потока 171,875 мс; запись с атомарной
метаинформацией чата — 20,808 мс, 49,1 операций/с, CPU 125 мс. Это короткий замер
на этой машине, не гарантия производительности и не измерение полной нагрузки/JNI.
Память и суммарные токены всех агентов: нет данных. Экономия делегирования не заявляется.

Проверка интеграции 23.10.2026: полный JVM-прогон — 309 тестов без ошибок/пропусков;
последующая проверка нативного Windows UI — 3 теста, включая поздние callbacks после
закрытия. Android API29/x86_64 — 14 instrumentation-тестов, в том числе два реальных
TLS/Signal узла, потеря ACK/повторы и изолированный снимок диалога. Lint: 0 ошибок,
18 предупреждений. После финальной визуальной правки повторно прошли 4 Android UI
теста и 3 Windows UI теста. Универсальный debug APK собран локально; ARM64 не запускался.
Windows app-image со встроенной Java21.0.12.1 запущен с отдельным тестовым профилем,
создал 15 снимков нативных экранов и завершился с кодом 0.

Интеграция 26.10.2026: listener чатов открывается вместе с приложением, а не только
при первом входе в раздел; адрес в приглашении подставляется из `LocalAddress`.
Полный локальный прогон — 312 тестов (core 188, messenger 12, desktop 112), 0 ошибок,
